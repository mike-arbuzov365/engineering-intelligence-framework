## Rule file format (current, not assumed)

Cursor's current, official project-rule mechanism is `.cursor/rules/*.mdc` -
one file per rule, any filename, organizable into subdirectories. A plain
`.md` file in that directory is **ignored** (no frontmatter to parse); the
`.mdc` extension is required for a project rule to be recognized at all.

Each `.mdc` file is YAML frontmatter followed by markdown content. The three
frontmatter fields and how they interact:

| `alwaysApply` | `description` | `globs` | Behavior |
|---|---|---|---|
| `true` | - | - | Always included in the model context; `description`/`globs` ignored |
| `false` | - | provided | Auto-attached when a matching file is in context |
| `false` | provided | omitted | Agent reads the description and decides whether to include it |
| `false` | omitted | omitted | Included only when `@`-mentioned in chat |

This adapter's generated file always sets `alwaysApply: true` - the closest
match to CLAUDE.md's unconditional autoload, chosen for parity with the
Claude Code adapter (see the parity matrix, `adapters/parity-matrix.json`).

### Legacy format: `.cursorrules`

A root-level `.cursorrules` file is Cursor's **legacy** mechanism -
confirmed deprecated (multiple Cursor forum threads describe an active
migration off it; current official docs do not mention it as a supported
format at all). This adapter does **not** generate or read `.cursorrules`.

### `AGENTS.md` (a separate, official alternative - not used by this adapter)

Cursor also supports a plain-markdown `AGENTS.md` in the project root (no
frontmatter, no scoping) as a simpler alternative to `.cursor/rules/`. This
framework's own repository already has a root `AGENTS.md` for a different
purpose (hand-authored contributor instructions for people/agents working
*on* this framework - see this repo's own `AGENTS.md`); this adapter targets
`.cursor/rules/` instead, deliberately, so a downstream project's own
`AGENTS.md` (if it has one) is never touched by EIF.

**Unverified, explicitly not relied on:** a web search surfaced a claim that
"Cursor reads CLAUDE.md the same way it reads AGENTS.md." This was checked
directly against the fetched official Rules page (full page text, plus a DOM
substring search for "CLAUDE.md") and found **not present** there. This
adapter does not depend on that claim, and it should not be repeated as fact
without separately confirming it against a current primary source.

## Why a dedicated EIF-owned file, not a shared one

`.cursor/rules/` genuinely supports multiple independently-named files, so
this adapter creates its own - `.cursor/rules/eif/governance.mdc` - rather
than modifying `AGENTS.md` or any other pre-existing `.cursor/rules/*.mdc`
file a project already has. Consequences of that choice:

- Project-owned Cursor rules are never touched, read, or enumerated by EIF.
- The dedicated file is marked `EIF-MANAGED. Do not hand-edit - fully
  regenerated by scripts/eif_init.py` and is regenerated wholesale on every
  init/upgrade (frontmatter included) - there is no marker-merge/preservation
  logic for it, because there is never legitimate project content inside it
  to preserve (unlike CLAUDE.md, which commonly has real project rules below
  the `EIF:END` marker).
- Switching away from Cursor deletes this file outright (see "Adapter
  switching" below), rather than leaving an empty husk behind.

## Nested entrypoint (generalized, not Cursor-specific)

`.cursor/rules/eif/governance.mdc` is three directories deep, none of which
exist on a fresh instance. `scripts/eif_init.py`'s transaction layer was
generalized (not hardcoded to this one path) to: record which of the
entrypoint's parent directories don't exist yet, create them, and - on any
failure, before or after commit - remove only the directories this run
itself created, deepest-first, never a pre-existing one. See
`scripts/tests/test_cursor_adapter.py` scenarios 2/2b for fault-injection
proof at multiple points, including a pre-existing `.cursor/rules/` (with an
unrelated project-owned rule file) surviving a fault untouched.

## Adapter switching

`claude-code -> cursor` and `cursor -> claude-code` are both supported via
`eif_init.py --force --adapter <name>`, in the same transaction as
everything else:

- The old entrypoint's EIF block is stripped (CLAUDE.md, if real
  project-owned content remains below `EIF:END`) or the whole file is
  deleted (Cursor's dedicated file, or a CLAUDE.md left with nothing but the
  EIF block itself).
- Malformed markers on the OLD entrypoint STOP the entire run before any
  file is written - never a partial switch.
- See `scripts/tests/test_cursor_adapter.py` scenarios 4-6.

## Skill discovery

**Not supported by this adapter.** Cursor's Rules mechanism has no
Claude-Code-Skills-equivalent auto-discovery verified this round; EIF does
not depend on it.
