# Маршрути і навички соло-EIF

**Мета.** Узгодити вибір глибини і правила для тестів у точках входу. Зробити один перелік навичок із визначеним впливом. Критерії статуту — A1, A2, A4.

## Підстава для рішення

Соло-розробник має витрачати увагу на продуктові рішення. Основний протокол дозволяє легку правку без планового файлу, а навичка планування може привести того самого виконавця до зайвого `task-scope.md`. Простеж один запит від правила до інструкції, яку отримає чат. Спосіб узгодити ці точки входу можеш обрати самостійно.

У звіті — [Як вибирати глибину](../../../2026-11-21-eif-sdd-review.uk.md#яку-глибину-планувати-соло-розробнику) · [Що показав аудит навичок](../../../2026-11-21-eif-sdd-review.uk.md#8-аудит-чинних-навичок).

Першоджерела — [Чинні маршрути EIF](https://github.com/mike-arbuzov365/engineering-intelligence-framework/blob/4e7e5d62ddb7d5b6c9723897eb30f9d2e824e104/playbooks/engineering-intelligence-operating-protocol.md) · [Умови пропуску етапів у SDD](https://github.com/genkovich/sdd/blob/b7e1e6ecdb9e38e1bccede006af7890f6d52a1f0/skills/_shared/size-matrix.md).

## Перед першою зміною

Прочитай [рішення](../03-DECISIONS-023-solo-agent-delivery.md) та записи за попередньою спробою. Звір актуальну базу й зачеплені матеріали: `playbooks/session-preparation.md`, `playbooks/execution-packet-planning.md`, `skills/`, `templates/agent-instructions*.md`, `src/engineering_intelligence_framework/service/task_kinds.json`. У налаштованому сховищі знайди попередні рішення за темою цієї сесії; запиши в завданні або контрольній точці джерело, результат і вплив. Якщо інстанс не управляє пам’яттю, використовуй правило його власника. У репозиторії фреймворку почни з реєстру рішень.

## Обсяг

Перевірити 12 основних, три початкові профільні навички, їхні посібники та компактні/звичайні інструкції. У гілках і приватних інстансах склад може різнитися. Для зачеплених записати: правило, власник джерела, контракт, матеріалізована версія, позитивний і негативний приклади. Для решти достатньо причини відсутності впливу. Виправити маршрути `light`, `structured`, `packet`; описати глибину всередині чинної структури, межі участі власника і модель за ризиком. Для дефекту розрізнити регресію, нечіткий критерій та відсутню вимогу. Коротке завдання може бути виконане окремо без запуску решти пакета.

Приватні навички використовувати для знеособлених випадків. До зміни правил відбитків окремо перевірити LF, CRLF і реальну зміну вмісту. Приватні скрипти не виконувати.

## Перевірка

Запускати з кореня чистої копії з відповідними встановленими залежностями та вихідним кодом цієї ревізії. На додачу відтворити критерій нижче на відповідній фікстурі. Для нової поведінки записати точну команду нового прикладу в поверненні.

```text
python -m engineering_intelligence_framework.cli skills check --framework-root .
python scripts/tests/test_operating_layer.py
python scripts/tests/test_project_skills.py
python scripts/tests/test_eif_mcp_compact.py
```

Контрольні випадки A1 для 006: одна очевидна правка тексту — `light`; регресія з перевіркою збереження та повторної спроби — `structured`; два залежні узгоджені кроки — компактний пакет; видалення поля публічного API — розгорнутий пакет з перевірками споживачів. Це очікування для нового контексту.

У знеособленому тесті відсутній контракт має окремий діагноз. Скрипт із закріпленими байтами LF проходить. І той самий текст із CRLF, і змінений скрипт відхиляються за відбитком. Політика збереження LF для скрипту з відбитком дає відтворювану робочу копію.
