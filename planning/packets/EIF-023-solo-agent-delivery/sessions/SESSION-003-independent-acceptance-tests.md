# Незалежні приклади приймання

**Мета.** До реалізації нового допуску визначити контрольні відповіді за правилами власника і прийняти сам набір тестів. Критерії статуту — A4, A5.

## Підстава для рішення

Мета окремого автора тестів — незалежно визначити, коли оркестратор має зупинитися. У прикладі зі звіту попередня сесія має `completed`, але її версію ще ніхто не прийняв. Ти можеш обрати контрольні дані й спосіб показати помилковий допуск. Очікувану поведінку виводь із критерію пакета.

У звіті — [Коли окупається незалежний автор тестів](../../../2026-11-21-eif-sdd-review.uk.md#7-коли-виділяти-тести-в-окрему-сесію) · [Три відтворені випадки вибору наступної сесії](../../../2026-11-21-eif-sdd-review.uk.md#3-готовність-mcp-до-експлуатації).

Першоджерела — [Чинне правило вибору сесії](https://github.com/mike-arbuzov365/engineering-intelligence-framework/blob/4e7e5d62ddb7d5b6c9723897eb30f9d2e824e104/src/engineering_intelligence_framework/service/packets.py) · [Роль автора тестів у SDD](https://github.com/genkovich/sdd/blob/b7e1e6ecdb9e38e1bccede006af7890f6d52a1f0/agents/test-author.md).

## Перед першою зміною

Прочитай [рішення](../03-DECISIONS-023-solo-agent-delivery.md) та записи за попередньою спробою. Звір актуальну базу й зачеплені матеріали: `scripts/tests/test_eif_mcp_packet_sources.py`, `scripts/tests/test_eif_mcp_eval.py`, `src/engineering_intelligence_framework/service/packets.py` як джерело поточного зовнішнього контракту; нові контрольні дані в тестах. У налаштованому сховищі знайди попередні рішення за темою цієї сесії; запиши в завданні або контрольній точці джерело, результат і вплив. Якщо інстанс не управляє пам’яттю, використовуй правило його власника. У репозиторії фреймворку почни з реєстру рішень.

## Обсяг

За вихідним посібником, рішеннями й критеріями скласти таблицю входів та очікуваних відповідей. Створити знеособлені пакети або локальні тести. Зберегти базову ревізію, команду, очікувану причину відмови, результат позитивного контролю та відбиток набору. Відсутність нового API не приймати за достатню невдачу: порівняти заявлену політику з фактичним старим прогресом або з навмисно некоректним правилом допуску на тих самих даних. Спробувати ослабити хоча б один суттєвий контроль у тимчасовому прикладі й перевірити, що це виявляється.

Автор тестів не реалізує продуктову функцію і не змінює чинні очікування заради проходження. Не зливати свідомо непрохідний обов’язковий тест в інтеграційну гілку.

## Перевірка

Запускати з кореня чистої копії з відповідними встановленими залежностями та вихідним кодом цієї ревізії. На додачу відтворити критерій нижче на відповідній фікстурі. Для нової поведінки записати точну команду нового прикладу в поверненні.


## Вихід і передача

- [ ] Є зрілі випадки: прийнята актуальна версія; `completed` без рев’ю; повернена спроба; інша ревізія після рев’ю; блокування попередньої навіть без залежності у суворому режимі; старий статус; повторний запит на ті самі дані. Для кожного є однозначна причина й очікувана наступна дія. Оркестратор окремо прийняв контрольний набір за його версією.
- [ ] На передачі додати точну команду для нового набору й очікування до реалізації. Підхід і результати тестів зберегти незалежно від історії чату.

До трьох ітерацій за цією перевіркою, зовнішніх запусків за замовчуванням нуль. При повторі тієї самої причини або зміні контракту поверни оркестратору факти й наступне рішення. Перед переходом між чатами онови та перевір `.session-context/eif-023-session-003.md`. При закритті зафіксуй долю сталого висновку у Knowledge Delta або підставу для його відсутності.

### Відтворення до реалізації

```text
python scripts/tests/eif023_admission_contract.py --baseline
python scripts/tests/eif023_admission_contract.py --controls
python scripts/tests/eif023_admission_contract.py --fingerprint
python scripts/tests/test_eif_mcp_packet_sources.py
python scripts/tests/test_eif_mcp_eval.py
```

`--baseline` на реальному читачі з цієї ревізії відтворив усі 13 відповідей прогресу. Порівняння його `next_session` з допуском дало очікуваний код 1 і дев’ять помилкових допусків, якщо трактувати прогрес як дозвіл. Наприклад, `FAIL completed_unreviewed: legacy next_session=SESSION-002; expected admission next_session=None (review_missing)`. Для `blocked_with_dependency` і `all_sessions_accepted` стара відповідь має однакову причину `completed_or_no_ready_session`. Новий контракт їх розрізняє.

`--controls` повернув код 0. Зі звіркою ревізії `accepted_current` дозволяє SESSION-002, а `stale_revision` зупиняє. Вимкнення лише цієї звірки залишає позитивний випадок зеленим, а для `stale_revision` програма фіксує фактичні `ready` і `SESSION-002` замість заборони. `test_eif_mcp_packet_sources.py` пройшов 9/9, `test_eif_mcp_eval.py` — 10/10. Це перевірки звичайною програмою без оцінювання відповіді моделі.

### Передача 004

Команда на майбутній реалізації `python scripts/tests/eif023_admission_contract.py --adapter scripts/tests/eif023_admission_reader_adapter.py`. Адаптер `open_case(data)` готує тимчасові джерела один раз на сценарій і повертає функцію їх читання. Вона приводить фактичні поля відповіді до `legacy` та `admission`. Назви причин у наборі задають зміст перевірки. Формат файлів, назви полів CLI/MCP і власні коди причин обирає 004. Повторний запит перевіряє однакове читання збережених даних двічі, а поведінку повторного запису визначає 004. Очікуваний результат на реалізації — 13 сценаріїв, 14 успішних читань, код 0. Окремі докази відповідності CLI і MCP, відновлення та конфлікту записів належать 004.

Сталий висновок для Knowledge Delta пакета — старий `next_session` відображає готовність за залежностями. Суворий дозвіл потребує поточної прийнятої спроби і ревізії навіть за прогресу `completed`. Доказ — контрольні випадки й наведена перевірка. Нового запису до реєстру рішень у цій сесії не потрібно.

Оркестратор прийняв спробу 1 та зафіксував відбиток набору до появи реалізації. Незалежно повторено `--baseline` (код 1, дев’ять хибних стартів), `--controls` (код 0, один очікуваний збій без звірки ревізії) та `--fingerprint` (збіг). Перевірка нового читача належить 004.
