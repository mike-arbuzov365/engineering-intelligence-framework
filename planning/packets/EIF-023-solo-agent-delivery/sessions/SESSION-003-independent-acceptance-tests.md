# Незалежні приклади приймання

**Мета.** До реалізації нового допуску визначити контрольні відповіді за правилами власника і прийняти сам набір тестів. Критерії статуту — A4, A5.

## Підстава для рішення

Мета окремого автора тестів — незалежно визначити, коли оркестратор має зупинитися. У прикладі зі звіту попередня сесія має `completed`, але її версію ще ніхто не прийняв. Ти можеш обрати контрольні дані й спосіб показати помилковий допуск. Очікувану поведінку виводь із критерію пакета.

У звіті — [Коли окупається незалежний автор тестів](../../../2026-11-21-eif-sdd-review.uk.md#7-коли-виділяти-тести-в-окрему-сесію) · [Три відтворені випадки вибору наступної сесії](../../../2026-11-21-eif-sdd-review.uk.md#3-готовність-mcp-до-експлуатації).

## Перед першою зміною

Прочитай [рішення](../03-DECISIONS-023-solo-agent-delivery.md) та записи за попередньою спробою. Звір актуальну базу й зачеплені матеріали: `scripts/tests/test_eif_mcp_packet_sources.py`, `scripts/tests/test_eif_mcp_eval.py`, `src/engineering_intelligence_framework/service/packets.py` як джерело поточного зовнішнього контракту; нові контрольні дані в тестах. У налаштованому сховищі знайди попередні рішення за темою цієї сесії; запиши в завданні або контрольній точці джерело, результат і вплив. Якщо інстанс не управляє пам’яттю, використовуй правило його власника. У репозиторії фреймворку почни з реєстру рішень.

## Обсяг

За вихідним посібником, рішеннями й критеріями скласти таблицю входів та очікуваних відповідей. Створити знеособлені пакети або локальні тести. Зберегти базову ревізію, команду, очікувану причину відмови, результат позитивного контролю та відбиток набору. Відсутність нового API не приймати за достатню невдачу: порівняти заявлену політику з фактичним старим прогресом або з навмисно некоректним правилом допуску на тих самих даних. Спробувати ослабити хоча б один суттєвий контроль у тимчасовому прикладі й перевірити, що це виявляється.

Автор тестів не реалізує продуктову функцію і не змінює чинні очікування заради проходження. Не зливати свідомо непрохідний обов’язковий тест в інтеграційну гілку.

## Перевірка

Запускати з кореня чистої копії з відповідними встановленими залежностями та вихідним кодом цієї ревізії. На додачу відтворити критерій нижче на відповідній фікстурі. Для нової поведінки записати точну команду нового прикладу в поверненні.

```text
python scripts/tests/test_eif_mcp_packet_sources.py
python scripts/tests/test_eif_mcp_eval.py
```

## Вихід і передача

- [ ] Є зрілі випадки: прийнята актуальна версія; `completed` без рев’ю; повернена спроба; інша ревізія після рев’ю; блокування попередньої навіть без залежності у суворому режимі; старий статус; повторний запит на ті самі дані. Для кожного є однозначна причина й очікувана наступна дія. Оркестратор окремо прийняв контрольний набір за його версією.
- [ ] На передачі додати точну команду для нового набору й очікування до реалізації. Підхід і результати тестів зберегти незалежно від історії чату.
