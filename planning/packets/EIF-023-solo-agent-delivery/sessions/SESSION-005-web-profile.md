# Вебзміна від критерію до доказу

**Мета.** У програмному профілі описати опціональні правила вебзміни й перевірити їх на одній завершеній поведінці. Критерії статуту — A6.

## Підстава для рішення

Вебпроєкт уже може мати токени, компоненти та власну перевірку їхньої версії. На прикладі повторного запиту після помилки зв’яжи вимогу з наявним компонентом і перевіркою через екран. Можеш обрати джерелом код, каталог компонентів або макет залежно від того, чим справді користується проєкт.

У звіті — [Дизайн-система, стани екрана й приклад AC-04](../../../2026-11-21-eif-sdd-review.uk.md#4-що-запозичити-з-sdd-для-веброзробки).

Першоджерела — [Каталог компонентів SDD](https://github.com/genkovich/sdd/blob/b7e1e6ecdb9e38e1bccede006af7890f6d52a1f0/skills/design-system/SKILL.md) · [Опис станів екрана SDD](https://github.com/genkovich/sdd/blob/b7e1e6ecdb9e38e1bccede006af7890f6d52a1f0/skills/screens/SKILL.md) · [Шаблон програмного профілю EIF](https://github.com/mike-arbuzov365/engineering-intelligence-framework/blob/4e7e5d62ddb7d5b6c9723897eb30f9d2e824e104/professional-profiles/software-development/templates/software-project-baseline.md).

## Перед першою зміною

Прочитай [рішення](../03-DECISIONS-023-solo-agent-delivery.md) та записи за попередньою спробою. Звір актуальну базу й зачеплені матеріали: `professional-profiles/software-development/`, `playbooks/`, `templates/`, `scripts/tests/` і відповідні встановлені матеріали. У налаштованому сховищі знайди попередні рішення за темою цієї сесії; запиши в завданні або контрольній точці джерело, результат і вплив. Якщо інстанс не управляє пам’яттю, використовуй правило його власника. У репозиторії фреймворку почни з реєстру рішень.

## Обсяг

Дати покажчик на наявні токени, компоненти, джерело макета чи приклад у коді та ревізію. У прикладі пов’язати критерій, стан екрана, компонент і тест. Використати повторний запит з клавіатури після помилки. Прийняти пояснення, чому новий компонент потрібен, або посилання на наявний. Для серверного чи текстового випадку перевірити умови пропуску зайвих матеріалів. Приватні імена та шляхи замінити публічним синтетичним прикладом.

Figma, Pencil, Storybook або новий компонент не є передумовами. Не змінювати приватні репозиторії в межах публічного пакета.

## Перевірка

Запускати з кореня чистої копії з відповідними встановленими залежностями та вихідним кодом цієї ревізії. На додачу відтворити критерій нижче на відповідній фікстурі. Для нової поведінки записати точну команду нового прикладу в поверненні.

```text
python -m engineering_intelligence_framework.cli skills check --framework-root .
python scripts/tests/test_operating_layer.py
python scripts/tests/test_package_smoke.py
```

## Вихід і передача

- [ ] На вебприкладі тест лише відповіді API призводить до повернення UI-критерію; проходження поведінки через інтерфейс дозволяє прийняти виправлення. Серверний приклад не вимагає жодного нового дизайну.
- [ ] Версія прикладу та доказ зі штатної точки входу, умови для повторення у виділеній власником копії вебпроєкту.

До трьох ітерацій за цією перевіркою, зовнішніх запусків за замовчуванням нуль. При повторі тієї самої причини або зміні контракту поверни оркестратору факти й наступне рішення. Перед переходом між чатами онови та перевір `.session-context/eif-023-session-005.md`. При закритті зафіксуй долю сталого висновку у Knowledge Delta або підставу для його відсутності.

## Перевірений приклад

[Необов’язковий вебпосібник](../../../../professional-profiles/software-development/playbooks/web-change-acceptance.md) зіставляє критерій, стан, компонент і перевірку. Для сервісної зміни зі сталою видимою поведінкою він залишає перевірку штатної відповіді сервісу. Наявний компонент та токен фокуса в прикладі зафіксовані у `scripts/tests/fixtures/eif_web/`.

Відтворення: `python scripts/tests/verify_eif_web_profile.py` з локально встановленим wheel EIF, Node та залежностями Playwright каталогу `site`. Для браузера Playwright достатньо встановити Chromium із цього каталогу. Для вже встановленого Edge можна вказати `EIF_BROWSER_CHANNEL=msedge`.

Програмна перевірка 3/3. Після підключення профілю з’явився закріплений посібник. Для першої версії API відповів 503 і 200, але CLI записав повернення AC-04 і зупинку наступної сесії. У Chromium 157.0.4341.60 негативний приклад не отримав фокус через Tab. Для другої версії Tab перейшов на Retry, Enter відкрив стани завантаження й успіху. CLI прийняв іншу ревізію та відкрив наступну сесію. Це синтетична перевірка через інтерфейс. Посібник фіксує стале правило про докази. Повторення на реальному вебпроєкті потребує виділеної власником копії.

Оркестратор прийняв спробу 1. Каталог навичок пройшов 15/15, перевірка операційного шару 232/232, встановлювана збірка 13/13.
